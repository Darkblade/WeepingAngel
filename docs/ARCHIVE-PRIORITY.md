# Foreground-priority archiving — 31 October 2026

Manual USB archive/removal now runs separately from the desktop foreground-operation state. Home navigation, thumbnails, camera settings and motion commands can be requested while a batch runs. A priority command gate gives waiting user commands precedence over background archive work. Archive holds its turn for one clip transaction (copy, validate/write, verify, current-manifest resolution, delete), releases it, then waits for a background turn for the next clip. It never interrupts a Blink command already in flight. Thus a user may wait for the current clip, but not every remaining clip. Manual batch cancellation is separate from foreground cancellation; closing cancels and waits for both. Automatic monitor manifest/module polling also uses background priority.

Manifests are refreshed after yielding to avoid reusing IDs invalidated by another client/foreground request. Pending archive clips pause for live view on their known module and resume when it closes; ordinary USB-list requests still report that a live module is busy. Multiple archive batches serialize to avoid duplicate active USB transactions. Progress exposes Waiting for archive turn; live-view pauses are logged.

Validation: deterministic tests show queued foreground work overtakes older background work, cancellation does not leak the gate, verified copy/delete of clip one precedes user action and then clip two, commands do not overlap, and live view pauses/resumes the remaining batch. Desktop interaction test confirms motion commands work while a manual archive task remains active. Full offline suite, desktop layout and embedded browser checks pass. No real Blink device settings were changed by tests.

Performance is separate from responsiveness. Blink client GeneralSleepTime defaults to3500ms. A manifest request waits before POST and before retrieving results, in addition to command polling; archive/removal normally fetches manifests before copy and again before deletion. Actual network payload transfer can therefore be short while per-clip processing takes tens of seconds. This release does not remove those compatibility delays or implement an unverified USB delete-all API. Whole-USB deletion could remove new/unselected clips or clips whose archive failed. Any future bulk cleanup must prove complete manifest coverage and deletion scope, preserve failed/new clips and verify all corresponding archives before destructive action.
